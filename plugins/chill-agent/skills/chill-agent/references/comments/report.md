# Report a result

Use this for a reply, explanation or outcome. Choose by what the user needs to
receive, not only whether you have a question. A requested investigation's
conclusion, a usable completed artifact, or a consequential decision belongs in
a Letter even when no reply is needed. Routine progress, supporting logs and
minor discussion belong in Comments. Follow an explicit user preference for the
channel and avoid a Letter for every internal task.

Lead with the result. Include the evidence, artifact link and material limitation
needed to use it. Keep the overall explanation in the Brief. A concise Letter
can point to an existing detailed Comment; do not copy the whole report again.
Keep one Letter format rather than adding consultation/notice categories. Do
not invent a question or require acknowledgement to deliver a result.

Save the message beside its Goal with `goal letter` or `goal comment`, using
installed help and a text file for longer content. Verify saving succeeded.
Neither action selects work, changes completion, or makes a pending Letter a
reason to stop authorized work. Keep the exchange in the user's language and
continue what can advance.

Web notifications alert on Letters, not Comments. For a saved Letter follow
[delivery](../notifications/deliver.md) using the saved preferences. Preparing or
sending a notification does not prove that the user saw it. Do not switch on
notifications, change routes, or retry an uncertain delivery on your own.

If reporting may have been missed, use [Review result delivery](review-delivery.md).
A no-work AutoContinue pass has only its internal result receipt, not a new Web
report; recovering a missing result Letter is actual work, not a no-work post.
